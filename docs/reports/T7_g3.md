## Remaining Limitations

### 1. Data Container Size Mismatch
**Issue**: Base class `FabMachineBlockEntity` has a final `data()` method returning a 4-slot `ContainerData` (energy, capacity, progress, ticks). G3 machines need additional UI data slots (formed state, paused state, water amount/capacity, vacuum pressure/spec, contamination phase).

**Impact**: Menu screens only receive the base 4 data values. Extra G3-specific UI data (indices 4-13) is not synced to clients.

**Planned Fix**: Implement custom packet-based syncing for G3-specific data in a follow-up. The `publishData()` method currently only writes base 4 slots; extra data fields are commented with TODO.

### 2. FoupContents.preparedG3 Integration
**Issue**: `completePrepJob()` in `G3ControllerBlockEntity` has a TODO placeholder. The actual G3 preparation result commitment via `FoupContents.preparedG3(cleanroomMeanPermille, drawsPermille)` depends on domain worker API not yet integrated.

**Impact**: Deposition etcher completes prep job but returns the admitted FOUP unmodified (no preparation applied). Cleanroom breach handling via `FoupDisposal.emptyCarrier()` is wired but untested.

### 3. Energy Check in Phase Pause Logic
**Issue**: `G3DepositionEtcherControllerBlockEntity.isPhasePaused()` uses `buffer().getAmountAsLong()` which reads stored energy, not available draw capacity. The base class `energySource().draw()` handles transactional draw correctly.

**Impact**: Phase pause may incorrectly report paused when energy is available but not drawn yet. Should use transactional draw check consistent with base class pattern.

### 4. Core Count Validation in Writer
**Issue**: `startWriterJob()` validates core count against `EUVCRAFTMod.settings().coreCountOptions()` but the recipe's output item carries the die type via `MaskData` component. Core count should be validated per die type requirements.

**Impact**: May allow invalid core counts for non-compute designs or reject valid ones.

### 5. Missing Block Item Registrations
**Issue**: G3 machine blocks (controllers, casing, modules, ports, panel, water inlet) need block item registrations in `ModItems.java` for creative tab and dropping.

**Impact**: Machines cannot be obtained in survival/creative without block items.

### 6. Structure Matcher Module Requirements
**Issue**: `G3StructureMatcher` requires at least one of each module type per machine kind:
- Writer: Writing Module + Metrology Module
- Deposition Etcher: Deposition Module + Rinse Module + Vacuum Module

**Impact**: Machines won't form without correct module placement. This is by design but module blocks must be registered and craftable.

### 7. Water Inlet Transactional Handler
**Issue**: `G3WaterInletHandler` implements `ResourceHandler<FluidResource>` but the transactional journal (`TankJournal.updateSnapshots`) is a no-op. The controller's `WaterTank` is used directly.

**Impact**: Fluid transactions may not rollback correctly on aborted inserts. The `WaterTank.fill/drain` are already transactional, but the handler should coordinate with the journal pattern used by `SupportWaterInletHandler`.

### 8. Vacuum Central Allocation
**Issue**: `tickVacuum()` allocates central vacuum using `CentralVacuumAllocator` with a single-element demand array. The cursor advances each tick but there's only one consumer (this machine).

**Impact**: Central vacuum allocation works but doesn't exercise multi-consumer round-robin. Real multi-machine central vacuum network requires coordinator integration.

### 9. Contamination Repair/Recalibration
**Issue**: `notifyStructuralBreach()`, `applyRepair()`, `recalibrate()` methods exist but depend on `MachineContaminationState` domain APIs. The repair cost parameters (material, UPW, FE) are not yet wired to actual item/fluid consumption.

**Impact**: Contamination state transitions work but repair actions don't consume resources.
